Контракт для любого AI-агента (Claude Code, Codex CLI и др.), работающего в этом репозитории. Обязателен к прочтению перед изменением кода. Читается автоматически большинством coding-агентов, если файл называется именно так.

## Обязательные проверки перед тем, как считать изменение готовым

Команды ниже must pass чисто (0 errors, clippy без предупреждений) перед коммитом. Запускай то, что затронуто изменением; при правках общих контрактов (формат операций, схема БД, команды Tauri) — всё.

Все гейты одной командой: `scripts/check.ps1` (`-Only frontend|desktop-rust|server`, `-KeepGoing`, `-Build`); скрипт сам находит Perl (или берёт `FOCUSNOOK_PERL`) и останавливается на первой ошибке. Те же проверки гоняет CI (`.github/workflows/ci.yml`) — он красный, значит изменение не готово.

Desktop (frontend + Tauri):

```
cd apps/desktop
npm run lint      # ESLint: границы слоёв (error) + бюджеты размера (warn)
npx tsc --noEmit  # типы
npm test          # Vitest
cd src-tauri
cargo fmt --check                           # формат (rustfmt); исправить: cargo fmt
cargo clippy --all-targets -- -D warnings  # unwrap_used/expect_used/panic/todo/unimplemented — deny, см. [lints.clippy] в Cargo.toml
cargo test
```

Сервер (`apps/server`), если менял его или контракт синхронизации:

```
cd apps/server
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
```

Предпосылки окружения:

- Компоненты: `rustup component add clippy rustfmt`.
- Первая сборка desktop-crate занимает 10+ минут (компиляция OpenSSL); не делай `cargo clean` без необходимости.
- На Windows `rusqlite` собирает SQLCipher с vendored OpenSSL, которому нужен **полноценный Perl** (например, Strawberry Perl) в `PATH`. Perl из Git for Windows (MSYS) не подходит — не хватает модулей (`IPC::Cmd`). Сервер (`apps/server`) Perl не требует.
- Если проверку нельзя запустить из-за окружения — прямо скажи об этом в отчёте/коммите, не выдавай непроверенное за проверенное.

`npm run lint` физически не даст импортировать `invoke`/store/window/event вне `src/shared/commands/` (правило `no-restricted-imports` в `eslint.config.js`). `cargo clippy` завалит сборку на `unwrap()`/`expect()`/`panic!()`/`todo!()` вне явно помеченного `#[allow(...)]` исключения (bootstrap в `lib.rs::run()`). Если линтер/clippy предлагают исключение — обосновывай явным `// eslint-disable` / `#[allow(...)]` с комментарием, а не молча игнорируй вывод.

## Границы слоёв (обязательно)

Поток зависимостей во фронтенде: **компоненты → хуки `src/shared/use*.ts` → `src/shared/commands/` → Tauri/Rust**. Обратных зависимостей нет.

- Компоненты React никогда не вызывают `invoke()`, `listen()` или API Tauri-плагинов напрямую — только через объект `commands` из `src/shared/commands` (каталог: по файлу на предметную область — `planItems`, `notes`, `reminders`, `serverSync`, …; `index.ts` собирает объект).
- Подписки на события Tauri — методы `on*` в `commands/*`, а в компонентах/хуках они подключаются через `useEventSubscription` (он корректно снимает слушатель при размонтировании).
- `#[tauri::command]` в Rust — только: валидация входа → вызов доменной функции/модуля → typed-результат. Обработчики лежат в `src-tauri/src/commands/<область>.rs` (зеркало `shared/commands/` на фронтенде; единственное исключение — команды синхронизации в `server_sync/`, рядом со своим протоколом), регистрируются в `generate_handler!` в `lib.rs`. Новую команду добавляй в файл своей области, а не в `lib.rs`. Бизнес-логика живёт в доменных модулях `src-tauri/src` (`plan_items`, `notes`, `reminders`, `sync_*`, `server_sync/` …), не в обработчике и не в `lib.rs`. Имена аргументов команды — часть контракта с фронтендом (Tauri сопоставляет их по имени из JS-payload): переименование — это изменение `shared/commands/` в том же коммите. Выделение `planner-core`/`planner-sync`/`planner-storage` в отдельные crates отложено на после v1 — новых crates сейчас не заводи без отдельного решения.
- Общий код кладётся в `src/shared/`; компоненты фичи — в её папку (`components/settings/`, `components/reminders/`, …). Фичи не лезут во внутренности друг друга: общее — через `src/shared/`.
- Доменные решения (статусы задач, конфликты синхронизации, правила переноса) принимает Rust. UI допускает только оптимистичное обновление с откатом при ошибке команды — как в `usePlanItems`/`useNotes`.
- Сервер контентно-слеп: он не расшифровывает пользовательские данные и не логирует их содержимое. Не добавляй серверную логику, которой для работы нужен открытый текст операций/вложений.

## SOLID в этой кодовой базе

- **S (Single Responsibility)** — один компонент/модуль = одна причина для изменения. `App.tsx` — только оркестрация shell; содержимое вкладок и настроек вынесено в `components/*`; логика состояния — в хуки, а не в разметку.
- **O (Open/Closed)** — новый sync/AI provider добавляется как новая реализация порта, а не веткой `if/else` в существующем коде.
- **L (Liskov)** — любая реализация порта заменяема без изменений в коде, который её вызывает.
- **I (Interface Segregation)** — `commands` дробится по предметным областям (по файлу на область), не собирается в один God-object.
- **D (Dependency Inversion)** — UI и use cases зависят от абстракций (`commands`, traits), не от конкретных Tauri/rusqlite/provider реализаций напрямую.

## Бюджеты кода

Проверяются ESLint как warnings (`eslint.config.js`); цель — не накапливать новые, а при касании файла с превышением — не ухудшать и по возможности чинить.

- Файл — до **300 строк** (без пустых и комментариев). Rust-файлы — тот же ориентир для боевого кода (тесты в `#[cfg(test)]`/`tests.rs` могут быть длиннее): превышение почти всегда значит «пора разделить по ответственности». Модуль, выросший за бюджет, превращается в каталог `module/` с реэкспортом по старым путям (пример: `server_sync/`). Данные (словари переводов — по файлу на язык; CSS — по областям в `src/styles/`) делятся так же.
- Функция/хук/команда — до **40 строк**; функция-компонент в `*.tsx` — до **80** (разметка раздувает счёт), при этом логика из неё уходит в хуки.
- Дублирование — повод для общего хелпера/хука, но не для абстракции «на будущее»: два места — терпимо, три — выноси.
- Performance-бюджеты (cold start ≤ 800 ms, idle RAM ≤ 120 MB и т.д.) обязательны к учёту: новая тяжёлая зависимость или фоновый процесс проверяются на соответствие, а не добавляются вслепую.
- Новая npm/cargo-зависимость добавляется только если оправдывает вес, а не ради одной мелкой функции.

## Тесты обязательны для нового кода

- Frontend: Vitest + React Testing Library (`npm test` в `apps/desktop`). Любая новая небезвизуальная логика (обработчики, вычисления, хуки) — минимум unit/component-тест по образцу `src/components/DayView.test.tsx`. Чистую логику выноси в `.ts`-модуль рядом с компонентом и тестируй напрямую (пример: `components/reminders/reminderTime.ts`).
- Rust: `cargo test` для доменной логики и серверных маршрутов. Команды, управляющие реальным окном (`toggle_overlay_layer` и подобные), пока тестируются вручную через живой запуск — мок-инфраструктуры для `tauri::WebviewWindow` нет; если пропускаешь автотест по этой причине, явно фиксируй это в коммите/PR.
- Рефакторинг — без изменения поведения: тесты до и после должны проходить в том же количестве; снапшоты (`src/__snapshots__`) не переписываются «чтобы позеленело».
- Ни один коммит не должен снижать существующее покрытие без явного обоснования.

## Локализация

- Любая новая строка UI добавляется в **все** локали (`src/shared/translations/<locale>.ts`; сейчас 10 языков) — эталон `ru.ts`/`en.ts`. Не оставляй английский текст в чужих локалях как «временный» без пометки в коммите.
- Ключи не конкатенируй из кусков; подстановки — через плейсхолдеры (`{minutes}`).

## Логирование

- Только `log::{error,warn,info,debug,trace}!` (инициализация — `tauri-plugin-log` в `lib.rs`); `println!`/`eprintln!` в боевом коде не допускаются. На сервере — `tracing`.
- Уровни: `error` — потеря данных или отказ функции; `warn` — восстановимый сбой/отложенная операция (повторяющийся сбой — один `warn` на серию, см. `FailureStreak` в `server_sync/engine.rs`); `info` — вехи жизненного цикла (старт, переключение профиля, итог цикла синхронизации); `debug`/`trace` — частые события (опрос планировщика, раунды обмена).
- В журнал — только идентификаторы (uuid), счётчики и длительности. Никогда: тексты задач/заметок/напоминаний, e-mail, имена, токены, пароли, ключи, полные пути с именем пользователя. Значения из `{err}` проверяй на утечки содержимого (ошибки разбора JSON могут цитировать данные).
- Нужно больше деталей при отладке — поднимай уровень (`FOCUSNOOK_LOG=debug`), а не добавляй временные `println!`. См. `docs/debugging.md`.

## Прод-уровень — проверять перед тем, как считать код готовым

- Никаких `unwrap()`/`expect()` в Rust вне `main`/`run()` bootstrap — везде `Result` с осмысленной обработкой ошибок.
- Решения по ошибке принимаются по её типу/коду, никогда по тексту (`error.contains("401")` — запрещённый приём: текст ошибки не контракт).
- Исходники — только UTF-8 без BOM. В Windows PowerShell 5.1 не правь их через `Get-Content`/`Set-Content` без `-Encoding utf8` — это портит кириллицу.
- Платформенный код (`#[cfg(target_os = "android")]`, `#[cfg(desktop)]`): импорты, нужные только одной платформе, гейтятся тем же `#[cfg]`, что и код, который их использует. Desktop-сборка не заметит пропавший Android-импорт (макрос `params!`, трейт `OptionalExtension` и т.п.), а Android-сборку локально проверить можно не всегда — при переносе такого кода сверяй импорты вручную.
- Секреты/токены никогда не коммитятся (release-ключ Android, `.env` сервера, admin-токен — вне репозитория); токены клиента — только в OS-хранилище/Keystore.
- Новые интерактивные элементы — с доступными именами (`aria-label`/`title`) и работают с клавиатуры (a11y).
- Любая новая UI-фича проверяется вручную перед тем как считается готовой: вёрстка/логика — через browser-preview на Vite dev server (`localhost:1420`), нативное поведение окна (transparency, always-on-top, drag) — через реальный запуск `desktop.exe`, потому что preview этого не покажет. Компиляция без ошибок — не то же самое, что «работает».
- Не имитировать законченность: если функциональность частична (реальный VDS rollout, физическая проверка Android-кандидата, юридическое одобрение — см. `docs/v1-release-plan.md`) — явно писать об этом в коде/коммите/доках, а не выдавать за готовую фичу.
