# Роадмап архитектурного оздоровления (для роя агентов)

Цель: убрать оставшуюся перегруженность, нарушения слоёв и логические риски,
ввести уместные современные паттерны и довести кодовую базу до состояния, в
котором LLM-агент:

- находит место изменения за один поиск;
- меняет один-два файла;
- проверяет себя одной командой.

Документ — рабочий план. Правила качества — [AGENTS.md](../AGENTS.md), карта
кода — [code-structure.md](code-structure.md), отладка —
[debugging.md](debugging.md), продуктовый статус —
[v1-release-plan.md](v1-release-plan.md).

## 0. Исходное состояние и цели (измеримо)

Метрики снимает `python scripts/metrics.py` (`--json` — для отчётов).

- Rust-метрики считаются только по боевому коду: всё до первого `#[cfg(test)]`, без `tests.rs` и `test_support.rs`.
- Строки считаются без пустых и `//`-комментариев.
- Карточки ссылаются на id метрик в критериях приёмки.
- Меняется определение метрики — меняется и baseline в этой таблице, в том же PR.

| Метрика | Что меряет | Baseline (2026-10-07) | Цель |
|---|---|---|---|

## 1. Протокол роя

### Роли

| Роль | Делает | Не делает |
|---|---|---|
| **Координатор** (1) | Выдаёт карточки по волнам; держит «замки» на горячих файлах; мержит; **единственный**, кто правит журнал (§5) и таблицу метрик (§0) | Не пишет код задач |
| **Исполнитель** (N) | Берёт одну карточку; работает в своём worktree и ветке `arch/<id>-<slug>`; доводит до зелёных гейтов | Не трогает файлы вне `Scope`; не правит журнал |
| **Ревьюер** (≥ 1 на карточку) | Независимо, только чтение: поведение до/после (`git show <base>:<file>`), слои, приватность логов, платформенные `cfg`, импорты для Android | Не правит код; пишет находки с `file:line`, классом CONFIRMED/SUSPECTED и сценарием отказа |
| **Верификатор** | После мержа волны: `scripts/check.ps1 -Build`, `python scripts/metrics.py --json`, сравнение с целями | — |

### Жизненный цикл карточки

1. **Взять.** Координатор назначает карточку и выдаёт замки на горячие файлы из её `Scope`.
2. **Baseline.** Исполнитель создаёт worktree от свежего `main`, прогоняет гейты затронутых частей и записывает числа тестов и метрик.
3. **Сделать** строго в пределах `Scope`. Рефакторинг без изменения поведения — отдельными коммитами от изменений поведения. Каждое изменение поведения перечислено в отчёте.
4. **Проверить.** Гейты зелёные, число тестов не меньше, целевые метрики сдвинулись, остальные не ухудшились.
5. **Отчитаться** в формате ниже, затем ревью. CONFIRMED-находки исправляются в той же ветке, потом повторное ревью.
6. **Мерж.** Координатор мержит, снимает замки, обновляет журнал и метрики.

### Формат отчёта исполнителя

```text
Карточка: <id>  Ветка: <branch>  База: <commit>
Сделано: <3–6 пунктов>
Файлы: <список; для крупных — строки до/после>
Гейты: frontend <PASS/FAIL, N тестов> · desktop-rust <…> · server <…> · CI <ссылка на run>
Метрики: M2 210→150, M3 344→260 …
Изменения поведения: нет | <список с обоснованием>
Не проверено: <Android-сборка, живое окно, …>
```

### Горячие файлы — не более одной карточки одновременно

- **Rust:**
  - `apps/desktop/src-tauri/src/lib.rs` (регистрация команд, `setup()`);
  - `apps/desktop/src-tauri/src/commands/mod.rs`;
  - `Cargo.toml` и `Cargo.lock` обоих крейтов — любая новая зависимость (`thiserror`, `proptest`, `specta`/`ts-rs`, `tauri` с фичей `test`).
- **Фронтенд:**
  - `apps/desktop/package.json` и `package-lock.json`;
  - `shared/commands/types.ts` и `shared/commands/index.ts`;
  - `shared/translations/*.ts` (новые ключи — во все 10 файлов одной карточкой);
  - `src/App.css` (порядок каскада).
- **Инфраструктура и доки:**
  - `.github/workflows/ci.yml`, `scripts/check.ps1`, `scripts/metrics.py`, `scripts/arch-check.py`;
  - `AGENTS.md`, `docs/code-structure.md`, `docs/v1-release-plan.md`, этот файл.

### Окружение

- Агентам нужен Perl для desktop-крейта: `FOCUSNOOK_PERL` или Strawberry Perl (см. debugging.md).
- У каждого worktree свой `target/`, первая сборка занимает ~10 минут (OpenSSL). На одной машине — не больше 2–3 Rust-исполнителей одновременно. Не делайте `cargo clean`.
- На машинах агентов нет Android NDK. Для полной Android-сборки есть `apps/desktop/scripts/android-build-windows.ps1`, но она требует установленного NDK. До появления F2 любая карточка, трогающая файлы с `#[cfg(target_os = "android")]`, обязана в ревью явно сверить импорты Android-веток. Был реальный случай: пропали `params!` и `OptionalExtension` в `server_sync/credentials.rs`.
- Кодировка: только UTF-8 без BOM. В Windows PowerShell 5.1 не используйте `Get-Content`/`Set-Content` без `-Encoding utf8` для правки исходников — так уже ломалась кириллица в комментарии.

### Definition of Done

- `scripts/check.ps1` зелёный по затронутым частям, при правке общих контрактов — целиком. CI зелёный.
- Число тестов не уменьшилось (кроме D1); для новой логики есть тесты.
- Целевые метрики карточки сдвинулись, остальные не ухудшились.
- Логи без пользовательского содержимого (AGENTS.md, «Логирование»).
- Доки обновлены в той же ветке: `code-structure.md` при изменении структуры, `AGENTS.md` или вложенные AGENTS.md при изменении правила, `debugging.md` при изменении логов или отладки, ADR для решений по зависимостям и контрактам.
- Отчёт ревьюера без открытых CONFIRMED.

## 2. Волны и зависимости

```text
F1 (коммит базы) ──► всё остальное
F2..F5, A1(ADR кодогенерации), D1(решение по запаркованному коду)  — параллельно после F1
A1 ──► C1 (ошибки) ──► C2 (кодогенерация) ──► C3 (ошибки во фронтенде)
C1 ──► B1 (MutationContext), B3 (репозитории), B4 (single-flight)
B2 (Session) ──► B1, B4
U2 (оптимистичный откат), U1 (аккаунт) ──► C3
S1 ──► S2 (стили)
B3 ──► Q2;  C2 ──► Q1;  I1 и R1 — после F1 в любой момент;  X1 — после решения владельца
P* — после релиза v1
```

Карточки с непересекающимися `Scope` и без общих горячих файлов внутри волны идут параллельно. Обозначения: **Risk** — L/M/H; **Depends** — что должно быть смержено до старта.

## 3. Карточки

### Волна F — фундамент

**F1. Коммит базы и первый прогон CI** · Risk L · Depends — · **блокирует всё**
- Why: весь предыдущий рефакторинг и этот роадмап не закоммичены (`git status`: `commands/`, `db/`, `profiles/`, `server_sync/`, `shared/commands/`, `translations/`, `styles/`, `scripts/`, `.github/` — untracked). Worktree от `HEAD` не содержит описанного кода.
- Scope: ≤ 6 коммитов по областям (frontend-рефакторинг; desktop-Rust-рефакторинг; логирование; инструменты и CI; `.gitattributes`; доки), push, первый прогон CI.
- Acceptance: `git status` чистый; на финальном коммите `scripts/check.ps1 -Build` 10/10; все job CI зелёные (ссылка на run). Если desktop-тесты, работающие с OS keyring, ведут себя на раннере иначе, это задокументировано, и такие тесты помечены `#[ignore = "<причина>"]`.

**F2. Android-проверка в CI** · Risk M · Depends F1
- Scope: job в `ci.yml`.
- Шаги:
  - NDK (`nttld/setup-ndk`) и `rustup target add aarch64-linux-android`;
  - переменные `CC_aarch64_linux_android`, `AR_aarch64_linux_android`, `RANLIB_aarch64_linux_android` на clang и llvm-ar из NDK — как в `apps/desktop/scripts/android-build-windows.ps1`; либо `cargo ndk`;
  - заглушка `../dist`, как в desktop-job;
  - `cargo check --target aarch64-linux-android`.
- Внимание: `cargo check` всё равно собирает C-часть OpenSSL и SQLCipher, это не бесплатно — кэшируйте `target`. Сначала спайк: нужен ли Gradle/Java при голом `cargo check` (ожидается, что нет). Запасной вариант — `npx tauri android build --debug --target aarch64`.
- Acceptance: job зелёный; проверочный PR с удалённым Android-импортом даёт красный job (ссылка на run в отчёте).

**F3. Архитектурные fitness-функции** · Risk L · Depends F1
- Scope: `scripts/arch-check.py`, подключение в `check.ps1` и CI.
- Pattern: правила зависимостей проверяет скрипт, а не память агента.
- Правила:
  1. `components/**` не импортирует `@tauri-apps/*` и внутренности чужой фичи (`components/notes/*` ↛ `components/settings/*`).
  2. Доменные модули (`plan_items*`, `notes*`, `reminders*`, `sync_*`, `alarms`, `db/`, `profiles/`, `server_sync/` кроме `account.rs`, `account_auth.rs`, `engine.rs`) не импортируют `crate::commands` и не используют `tauri::State`. Исключение задокументировано: команды синхронизации живут в этих трёх файлах.
  3. После B3 `*/rules.rs` не импортирует `rusqlite`.
  4. Новый файл выше бюджета M1 — ошибка, существующий — предупреждение.
  5. Пути, упомянутые во вложенных AGENTS.md (F4), существуют.
  6. Исходники в UTF-8 без BOM, без характерных кракозябр (`Р°`, `РЅ`, `вЂ`).
- Acceptance: скрипт выполняется < 5 с; проверочный коммит с нарушением каждого правила ловится; на текущем коде — 0 ошибок.

**F4. Вложенные AGENTS.md** · Risk L · Depends F1
- Scope: `apps/desktop/src/AGENTS.md`, `apps/desktop/src-tauri/AGENTS.md`, `apps/server/AGENTS.md`, рядом `CLAUDE.md` с `@AGENTS.md`; ссылка из корневого AGENTS.md.
- Содержание (≤ 80 строк):
  - рецепты «где что менять» с конкретными путями: новая команда; новая сущность; новая строка UI; новая миграция; новое событие;
  - локальные инварианты, например порядок блокировок;
  - команды проверки этой части.
- Acceptance: каждый рецепт выполним без поиска по коду (ревьюер проходит один рецепт вслепую); пути проверяет F3, правило 5.

**F5. Шапки модулей** · Risk L · Depends F1 · параллельно по каталогам
- Scope: каждый `.rs` в `src-tauri/src` и `apps/server/src` начинается с `//!` (1–5 строк: назначение, кто вызывает, инварианты); каждый `shared/*.ts` — с `/** */`.
- Acceptance: проверка скриптом (правило в F3): 100% `.rs` с `//!`-шапкой длиной 1–5 строк; шапки фиксируют «зачем» и инварианты, а не пересказ кода.

**D1. Решение по запаркованному и мёртвому коду** · Risk M · Depends F1 · **решение владельца**
- Why:
  - `cloud_sync.rs` (594 строки), `sync.rs`, `oauth.rs`, `sync_tokens.rs` и 18 их тестов компилируются только с фичей `cloud-providers`, которую CI не включает;
  - 4 команды объявлены, но не зарегистрированы (M6b − M6), при этом фронтенд вызывает `connection_status`, `disconnect_provider`, `start_provider_auth`, `sync_cloud_now` (`shared/commands/sync.ts`);
  - `serverSync.syncNow` / `sync_server_now` не используются UI.
- Варианты:
  - (a) добавить `cargo check/test --features cloud-providers` в CI и держать код живым;
  - (b) удалить запаркованный код и мёртвый фасад, сохранив историю в git (тег `parked/cloud-providers`).
- Acceptance: решение записано в ADR; M6b = M6; в TS нет вызовов незарегистрированных команд; при (b) перечень удалённых тестов — в отчёте.

### Волна A/C — контракты и ошибки (A1 → C1 → C2 → C3)

**A1. ADR: кодогенерация контракта** · Risk L · Depends F1 · параллельно с F
- Scope: `docs/adr/0001-contract-codegen.md`, без кода (спайк в отдельной ветке не мержится).
- Варианты:
  - `tauri-specta` + `specta` — типы и типизированные команды; генерируемый клиент возвращает `Result`-объекты, а не бросает исключение;
  - `ts-rs` — только типы, плюс рукописные обёртки и контрактный тест имён команд против `generate_handler!`.
- Критерии: стабильная версия для Tauri 2 на момент решения (если её нет — фиксировать риск RC); вес в сборке; работа с `cfg`-командами; влияние на форму ошибок, на которую опирается C3.
- Acceptance: ADR с решением и описанием, как `AppError` из C1 будет представлен в TS (например, нужен ли `derive(specta::Type)`).

**C1. Типизированные ошибки в desktop-Rust** · Risk M · Depends A1 · несколько PR последовательно
- Scope: `src-tauri/src/error.rs`, затем перевод по областям.
- Pattern:
  - `thiserror`-перечисление `AppError` с вариантами `Db`, `Io`, `Crypto`, `Validation`, `NotFound`, `Unauthorized`, `SessionLocked`, `Poisoned` (отравленный `Mutex`), `Network`, `Server { status }`;
  - `impl Serialize` в `{ code, message }`, в Tauri 2 тип ошибки команды обязан быть `Serialize`;
  - `From<rusqlite::Error>` и другие `From` вместо `map_err(to_string)`;
  - `type AppResult<T> = Result<T, AppError>`;
  - хелпер `lock(&mutex) -> AppResult<Guard>`.
- Порядок PR:
  1. `error.rs` и хелперы;
  2. по PR на область: plan_items, notes, reminders, profiles, server_sync;
  3. доменные модули.
- Обязательно: `server_sync/account_auth.rs:101` сейчас сопоставляет ошибку по тексту (`error.contains("401")`), чтобы откатиться на авторегистрацию. Это заменяется проверкой `AppError::Unauthorized` с отдельным тестом, иначе C1 молча сломает регистрацию.
- Acceptance:
  - M2 ≤ 20, M3 ≤ 20;
  - тест сериализации для каждого `code`;
  - фронтенд не показывает сырые строки бэкенда: каждый `code` маппится на ключ i18n (C3);
  - логи без содержимого;
  - Android-импорты проверены (F2).

**C2. Сгенерированный контракт TS ↔ Rust** · Risk M · Depends C1
- Scope: по ADR A1:
  - генерация `shared/commands/bindings.ts` (коммитится; CI проверяет актуальность через `git diff --exit-code`);
  - фронтенд-типы (`ThemeMode`, `Locale`, `ResizeDirection`, `NoteFolderSort`, `FolderRailSide`, `CursorClientPosition`) переезжают в `shared/types.ts`;
  - `shared/commands/<area>.ts` остаётся фасадом для компонентов поверх сгенерированного клиента.
- Acceptance: M5 = 0 (рукописного `types.ts` больше нет); контрактный тест: каждая команда, вызываемая из TS, зарегистрирована в `generate_handler!` с теми же именами аргументов.

**C3. Обработка ошибок во фронтенде** · Risk M · Depends C2, U1, U2
- Scope: `shared/` — `runCommand`/`useCommandMutation` и единый неблокирующий показ ошибок; перевод всех M4-мест.
- Pattern: `catch` различает ожидаемое («вне Tauri», «нет сети», `SessionLocked`) и баги по `code`. Ожидаемое помечается `// expected: <почему>`, баги показываются пользователю (строки во все 10 локалей) и пишутся в `console.error` в dev.
- Acceptance: M4 = 0; каждый хук данных имеет тест «ошибка команды → состояние ошибки». Тест отката не дублирует U2.

### Волна B — слои бэкенда

**B2. `Session`: атомарная смена профиля и защита фоновой синхронизации** · Risk **H** · Depends F1 (лучше после C1)
- Why:
  1. Последовательность «открыть vault → идентичность устройства → `HlcClock` → ключ аудио» продублирована в `lib.rs::run` (`setup()`) и `commands/profiles.rs::install_vault`.
  2. `install_vault` меняет `Db`, затем часы, затем ключ аудио под разными блокировками, то есть неатомарно. Параллельный код может увидеть новое соединение со старыми часами — комментарий в `commands/profiles.rs` прямо это запрещает.
  3. `server_sync/engine.rs::run_sync_cycle` один раз запоминает профиль, учётные данные и ключ, а затем ~8 раз заново берёт `db.0` между `await`. Смена профиля посреди цикла приводит к тому, что операции и курсоры профиля A записываются в хранилище профиля B.
- Pattern:
  - application service + generation guard;
  - `session::Session { conn, clock, audio_key, profile_id, generation }` под одной блокировкой, установка — одной функцией `session::install(...)`, её вызывают и `setup()`, и команды профилей;
  - цикл синхронизации сверяет `generation` после каждого `await` и прерывается при смене.
- Изменение поведения, которое нужно явно решить и описать: `setup()` вызывает `restore_android_alarms`, а `install_vault` — нет. Сейчас после смены профиля на Android остаются будильники старого профиля и не ставятся будильники нового. Целевое поведение: при смене снимать будильники старого профиля и ставить нового.
- Тестируемость: `session` принимает простые типы (без `tauri::State`), ключи — через трейт с тестовой реализацией вместо OS keyring.
- Acceptance:
  - `db::open`, `ensure_device_identity`, создание `HlcClock`, получение ключа аудио вызываются ровно из `session`;
  - тест «смена профиля во время цикла синхронизации → цикл прерван, в новом профиле нет чужих операций»;
  - тест атомарности (соединение и часы всегда одного профиля);
  - Android-job F2 зелёный;
  - ручной запуск `npm run tauri dev` со сменой профиля описан в отчёте.

**B1. `MutationContext` для команд-мутаций** · Risk M · Depends C1, B2
- Scope: `commands/mod.rs`, `commands/{plan_items,notes,reminders,profiles}.rs`.
- Why: M7 = 56 прямых блокировок; 19 команд повторяют «lock db + lock clock + активный профиль + вызов + drop + `trigger_server_sync`».
- Pattern: Unit of Work — `commands::mutate(&app, |ctx| …) -> AppResult<T>` поверх `Session` из B2. Синхронизация ставится в очередь только после успешного завершения и после снятия блокировок. Чтения — через `commands::read(&app, |conn| …)`.
- Acceptance: M7 ≤ 3; ни одна команда, кроме хелпера, не вызывает `trigger_server_sync` напрямую; тест хелпера: при ошибке синхронизация не запускается, при успехе запускается ровно один раз; мутационная команда занимает 1–5 строк.

**B3. Репозиторий + чистые правила для сущностей** · Risk M · Depends C1 (все PR смержены) · параллельно по сущности
- Scope: `plan_items.rs`, `notes.rs`, `reminders.rs` → каталоги `<entity>/{mod,repo,rules}.rs` (+ `tests.rs`).
- Pattern:
  - `repo.rs` — только SQL и маппинг строк;
  - `rules.rs` — чистые функции без `rusqlite` (цикл статусов, перенос на другую дату, правила долгоживущих задач, валидация времени напоминания);
  - `mod.rs` — операции, связывающие repo, rules и `sync_log::record_operation` в одной транзакции.
- Публичный API `crate::<entity>::*` сохраняется через реэкспорт в `mod.rs`, чтобы B1 не конфликтовал.
- Acceptance: `plan_items` выходит из M1; `rules.rs` не импортирует `rusqlite` (F3, правило 3); для каждой `pub fn` в `rules.rs` есть тест без БД; тесты атомарности `create_is_atomic_when_the_operation_log_write_fails` (`plan_items`, `reminders`) проходят без изменений.

**B4. Single-flight для синхронизации** · Risk M · Depends C1, B2

- Why: `sync_server_now` обходит `SYNC_IN_FLIGHT` и может идти параллельно с фоновым циклом. При этом UI его не вызывает (см. D1).
- Варианты: удалить мёртвую команду (если D1 так решит) или сделать single-flight — ручной запуск ждёт текущий цикл или ставит флаг повтора.

**U2. Корректный оптимистичный откат** · Risk M · Depends F1
- Scope: `shared/usePlanItems.ts`, `useNotes.ts` (включая `editNote`), `useReminders.ts` → общий `useOptimisticList`.
- Why: откат через захваченный снимок `previous` теряет параллельные изменения.

- Pattern: обратная операция для конкретного элемента (вернуть удалённый на его позицию, восстановить прежнее значение поля) через функциональный `setState`.
- Acceptance: тесты: две параллельные мутации с ошибкой одной — вторая сохраняется; синхронизация во время мутации не затирается. Публичное API хуков не меняется.

### Волна I / X — локализация и безопасность

**I1. Гейт полноты локализации** · Risk L · Depends F1 · **объём перевода — решение владельца**
- Why: M12 = 936. Восемь локалей переведены на 86–104 ключа из ~206, остальное — английский fallback через `makeDictionary`. Тесты проверяют только выборочные списки ключей, поэтому правило «новые ключи во все 10 файлов» сейчас не проверяется.
- Scope: тест на M12 «не растёт» (снимок количества непереведённых ключей по локали); по решению владельца — перевод с пометкой «требует вычитки носителем».
- Acceptance: добавление ключа только в `ru`/`en` роняет тест; снимок обновляется только осознанно, в PR перевода.

**X1. Ключ медиа и сквозное шифрование** · Risk **H** · Depends F1 · **ADR + решение владельца, затрагивает протокол и сервер**
- Why:
  - клиент отправляет пароль на сервер (`server_sync/protocol.rs`), а ключ шифрования операций и вложений — `Argon2(password, sha256(email))` (`blob_crypto.rs::derive_media_key`), так что оператор сервера технически может вывести ключ;
  - при ошибке Argon2 происходит молчаливый откат на одиночный SHA-256;
  - nonce AES-GCM берётся из UUID v4, где часть битов фиксирована (версия и вариант), вместо 96 случайных бит.
- Публичные тексты обещают «шифрование на клиенте», а не недоступность данных оператору — ложного обещания нет, но это слабость дизайна.
- Pattern (варианты для ADR):
  - разные производные секреты для аутентификации и для шифрования (например, HKDF с разными контекстами, на сервер уходит только auth-секрет);
  - либо случайный media key, обёрнутый ключом из пароля и хранящийся на сервере в обёрнутом виде;
  - nonce из CSPRNG; удалить fallback на SHA-256.
- Обязательно: план миграции уже зашифрованных данных и учёток (версия формата `FNSB` / `kdf_version`); совместимость старых клиентов; обновление `legal.rs` и `docs/store-listing/*` только при реальном изменении — с пометкой о юридической вычитке.
- Acceptance: ADR принят владельцем; тест «сервер, зная всё, что ему отправляют, не может расшифровать payload» на уровне модели протокола; миграционный тест старый формат → новый; запись в v1-release-plan.

## 4. Принципы для LLM-сопровождения (во всех карточках)

- **Один файл — одна ответственность, ≤ 300 строк.** Агент читает файл целиком за один вызов.
- **Предсказуемые места.** Структура зеркальна: `shared/commands/<area>.ts` ↔ `commands/<area>.rs` ↔ `<entity>/{repo,rules}.rs`. Новое кладётся по рецептам вложенных AGENTS.md (F4).
- **Явное лучше неявного.** Без реэкспортов «для старых путей», без лишней макромагии, без глобального состояния вне `tauri::State`/`Session` и задокументированных `static`.
- **Ошибки — данные, а не строки.** Решения принимаются по типу или `code` (C1), никогда по тексту ошибки.
- **Контракты генерируются** (C2) и проверяются в CI; протокол клиента и сервера закреплён общими фикстурами (Q1).
- **Правила проверяются скриптами:** ESLint, clippy, rustfmt, `arch-check.py` (F3), `metrics.py`. Если правило нельзя автоматизировать — оно в AGENTS.md с примером.
- **Тесты — исполняемая спецификация.** Имена описывают поведение, чистые правила тестируются без БД и окна.
- **Шапки модулей** (F5) — «зачем» и инварианты.
- **Решения — в ADR** (`docs/adr/NNNN-*.md`, ≤ 1 страницы: контекст, решение, последствия) для зависимостей, контрактов, безопасности и удаления кода.
- **Логи — диагностический интерфейс:** стабильные сообщения, уровни по AGENTS.md, без содержимого пользователя; повторяющийся сбой — один `warn` на серию.
- **Не имитировать законченность.** Непроверенное (Android, живое окно, CI) — в отчёте и в v1-release-plan.
